A front desk, a workshop, and a blueprint

02 / One command, end to end

From words to a saved box

The CLI handles the outside edges: arguments in, file and result out. The core owns the actual modeling decision.

01 · PARSE

Read the command and convert dimensions from text to numbers.

02 · VALIDATE

Ask the core to reject empty names or dimensions that are not positive finite values.

03 · UPDATE

Assign a stable ID and add the box to the scene object list.

04 · SAVE

Serialize the scene and write the JSON file; report the new ID.

Try it
cargo run -p plumb-cli -- new scene.json
cargo run -p plumb-cli -- add-box scene.json block 2 3 4
cargo run -p plumb-cli -- move scene.json 1 1 0 0
cargo run -p plumb-cli -- inspect scene.json

Kitchen analogy

The CLI is the waiter taking an order. It does not decide whether an ingredient is safe. The core is the kitchen: it checks the request, changes the recipe, and sends back the finished dish.

Why share the core? A future viewport and agent tool should get the same result from the same operation.

03 / The scene model

A scene is a small address book of objects

Each object has a durable address, a human name, a location, and a shape. The ID is the dependable handle.

AanameA label for people, such as “block”.

◇GeometryToday, the enum has one shape: Box.

Library analogy

The object ID is like a library catalog number. A book can move to a different shelf without changing its catalog number. Likewise, an object can move or shift its position in the vector without changing its identity.

Current model limits: boxes only; position and dimensions are supported, while rotation, materials, deletion, and resize operations are not implemented yet.
04 / The core engine

The core is both the rulebook and referee

Public methods are the gates into scene changes. Data from a file is checked again after parsing, because saved files can be edited or malformed.

When adding a box

  1. Trim-check the name.
  2. Check each dimension is finite and greater than zero.
  3. Reserve the next ID, guarding against integer overflow.
  4. Add the object at position zero.

add_box(name, size) → Result<ObjectId, SceneError>

When moving an object

  1. Reject NaN or infinite coordinates.
  2. Find the object by stable ID.
  3. Return ObjectNotFound if no matching ID exists.
  4. Change the position only after validation passes.

set_position(id, position) → Result<(), SceneError>

SceneError

A named outcome such as invalid dimensions or missing object. It gives callers something to report.

HashSet of IDs

During file validation, a temporary set catches duplicate IDs. Think of it as a guest list that rejects repeated names.

Important boundary

Validation lives in plumb-core. The CLI is not trusted to be the only caller.

    "id": 1,

    "position": {"x": 1, "y": 0, "z": 0},
    "geometry": {
      "type": "box",
      "geometry": {"size": {"x": 2, "y": 3, "z": 4}}
    }
  }]
}

How failures travel

A file error or core error becomes a readable message in main. The message goes to stderr and the program returns a failure exit code.

Airport security analogy

Parsing checks that the suitcase has the right shape. Scene validation checks that its contents obey the rules before it enters the workshop.

Serialization uses Serde derives. The scene format is versioned, and the loader rejects versions other than 1 today.

07 / Reading the code

A quick map through lib.rs and main.rs

plumb-core/src/lib.rs, top to bottom

ObjectId and Vec3 define small value types.

BoxGeometry, Geometry, and Object describe a scene item.

Scene owns a version, next ID, and object vector.

SceneError gives failures readable names.

impl Scene exposes create, lookup, move, encode, decode, and validation.

#[cfg(test)] keeps unit tests beside the behavior they protect.

plumb-cli/src/main.rs, top to bottom

main turns success or failure into a process exit code.

run matches the command name and performs its workflow.

required and number parse positional inputs.

read_scene reads text, then calls core deserialization and validation.

write_scene serializes and writes JSON.

usage is the CLI help text.

Code-reading analogy

Start with the public API like reading a building's front entrance sign. Then follow one CLI command into that API. You can understand the supported behavior without first reading every helper.

There are three core unit tests: create/move/JSON round-trip, invalid dimensions/positions, and invalid scene IDs. The CLI currently has no automated tests.
08 / The roadmap

Five milestones, five concrete outcomes

Each milestone adds a usable layer while keeping one modeling engine authoritative.

1
Core Engine and CLI foundation mergedFinish dependable CLI behavior and tests so people, scripts, and existing agents can create, inspect, change, validate, and save scene files.
2
Desktop Viewport plannedOpen those same files in a read-only 3D viewer. Users can visually inspect objects and refresh scenes edited through the CLI.
3
Interactive Modeling plannedSelect, move, resize, snap, undo, redo, and save changes with the same core rules and reliable file synchronization.
4
AI-Agent Integration plannedOffer structured, validated tools and optional MCP transport after the CLI and operation contracts are dependable. Users bring their own agent.
5
Production Readiness and Release plannedAdd CI, installation and contribution docs, format compatibility guidance, end-to-end verification, packaging for chosen platforms, and a practical first-release checklist.
Current CLI details: inspect emits JSON, while add-box reports success as plain text. Help is global, extra arguments are not consistently rejected, and scene writes use a direct file write. Consistent JSON results and errors, strict argument handling, safer writes, object queries, and CLI workflow tests are roadmap work. The desktop app and dedicated structured agent transport do not exist yet.
09 / Honest boundaries

What exists now, and what comes next

implemented

A useful small base

Rust scene data, stable IDs, box creation, position changes, validation, version 1 JSON load/save, and CLI commands for new, add-box, move, and inspect.

The CLI uses the same public core operations that future interfaces should share.

planned

Next layers

Agent-ready output conventions, object-level queries, desktop visualization and editing, undo/redo, optional structured tools, packaging, and richer workflows.

Those capabilities are tracked in GitHub milestones; they are not present just because they appear in the roadmap.

The Plumb idea

Plumb provides the workshop and its dependable tools. You choose who gives the instructions, whether that is you, a shell script, or an AI agent you already trust.
